# ADR-001: Стек и хранилище

Статус: proposed
Дата: 2026-10-30
Контекст: spec 1.0 утверждена; roadmap 2.2. Ключевые силы:
- Полнотекстовый поиск с русской и английской морфологией, нормализацией, алиасами тегов и ранжированием по приоритету полей (FR-10, Р2); ответ ≤ 5 с p95 (NFR-2).
- Масштаб MVP мал: ≤ 1 000 участников, ≤ 50 одновременных сессий (NFR-4) → объём данных порядка тысяч анкет `[умозаключение]`.
- Транзакционная целостность: матч при взаимной оценке — атомарная проверка+вставка (FR-7); удаление анкеты каскадом (FR-17); журналы с годовым хранением (NFR-10).
- Клиент — Telegram Mini App (NFR-11), backend единственный, отдельного search-кластера команда MVP не потянет `[предположение: команда 1–2 разработчика]`.

## Альтернативы

| Вариант | Плюсы | Минусы | Стоимость выхода |
|---|---|---|---|
| A. PostgreSQL (tsvector/pg_trgm) | FTS с рус./англ. словарями из коробки (FR-10); транзакции и FK для матчей/удалений; один компонент — минимальная эксплуатация; алиасы тегов — обычные таблицы; создатель ранга по приоритету полей через веса tsvector | Ранжирование и морфология слабее спец. движков; тонкая настройка весов — ручной SQL | Средняя: SQL-запросы поиска привязаны к PG-функциям; данные портируемы дампом |
| B. PostgreSQL + внешний search-движок (Elasticsearch/OpenSearch/Typesense) | Лучшая морфология/ранжирование; масштабируемость поиска | Второй stateful-компонент: синхронизация индекса, консистентность, эксплуатация; избыточно для 1k анкет | Высокая: двойная запись/CDC, переезд схем индекса |
| C. SQLite (FTS5) | Нулевая эксплуатация; FTS5 есть | Нет русского словаря/стемминга из коробки; слабая конкурентная запись; риск по NFR-4 (50 сессий) и росту | Средняя: миграция на клиент-серверную СУБД почти неизбежна при росте |
| D. MongoDB | Гибкая схема под анкету | Текстовый индекс слабее PG для русской морфологии `[непроверено]`; транзакции и join-логика матчей менее естественны | Средняя |

## Критерии

- Полнотекстовый поиск рус./англ. с ранжированием по полям (FR-10) — обязательно.
- Атомарность матча и каскадного удаления (FR-7, FR-17).
- Число stateful-компонентов — минимум (эксплуатация MVP).
- Стоимость выхода при росте за пределы NFR-4.

## Решение-кандидат

**Вариант A: PostgreSQL 16** как единственное хранилище.

- Поиск: `tsvector` с конфигурациями `russian`/`english`, веса по приоритету полей (навыки A > проекты B > проф. интересы C > личные интересы D); точное совпадение тега — отдельный буст до FTS-ранга (FR-10). Триграммы `pg_trgm` — для автодополнения тегов (FR-4).
- Нормализация (регистр, `ё`→`е`, пробелы) — на запись в приложении + нормализованные колонки (см. 01-domain-model).
- Язык backend — отдельный микро-выбор, не влияющий на хранилище (поисковая логика в SQL):

| Вариант | Плюсы | Минусы |
|---|---|---|
| Python 3.12 + FastAPI + SQLAlchemy/asyncpg, миграции Alembic | Быстрее MVP-код; Pydantic-валидация схем из коробки | Больше памяти; деплой через venv/uvicorn |
| Go 1.23 + chi/net-http + sqlc/pgx, миграции goose | Один статический бинарник; меньше память; сильнее конкурентность (бот + ретраи уведомлений) | Больше бойлерплейта; медленнее старт MVP |

`[предположение]` для обоих — решение за владельцем по языку команды; кандидатом остаётся Python, Go — равноправная альтернатива. Клиент Mini App: React + TypeScript `[предположение]`.

Решение — кандидат до принятия владельцем.

## Принятые компромиссы (trade-offs)

- Ранжирование поиска — вручную на SQL, а не из коробки движка; сложность запросов выше.
- Рост > ~10k анкет или требования к нечёткому поиску → пересмотр в пользу варианта B (условие пересмотра ниже).
- Стек языка зафиксирован предположением, не проверенным с командой.

## Риски

| Риск | Severity | Митигация |
|---|---|---|
| Качество FTS-ранжирования PG не устроит по AC-5 | medium | AC-5 проверяем тестовым корпусом запросов до фазы 3; запасной путь — вариант B без смены схемы данных |
| Единая точка отказа БД против NFR-6 (99%/мес) | low | Минимальный managed Postgres или патронаж/бэкапы; 99%/мес допускает ~7ч простоя — достижимо без HA-кластера `[умозаключение]` |
| `ё`→`е` и двуязычие в одном tsvector | low | Нормализация на запись; мультиконфигурационный tsvector (рус.+англ.) — проверить спайком в фазе 3 |

## Основания (evidence)

- FR-10 (нормализация, словари, приоритеты полей), NFR-2, NFR-4, NFR-5 — [03](../requirements/03-functional-requirements.md), [04](../requirements/04-non-functional-requirements.md).
- Доменная модель: [01-domain-model.md](01-domain-model.md).
- Решение Р2 (Postgres как кандидат упомянут в roadmap 2.2 как направление).

## Условия пересмотра (reopen conditions)

- Рост прогноза участников > 10 000 или p95 поиска > 5 с на тестовом корпусе.
- Требование нечёткого/семантического поиска (эмбеддинги) — отдельный ADR.
- Команда не подтверждает Python — пересмотр только языковой части, хранилище не затрагивается.

## Открытые вопросы

1. Язык/фреймворк backend — решение владельца: Python+FastAPI (кандидат) или Go (равноправная альтернатива); на хранилище не влияет.
2. Хостинг БД (managed/self-hosted) — отложено до ADR по развёртыванию или решения владельца; место хранения ПДн должно быть задокументировано (NFR-10).
3. Нужен ли спайк FTS-ранжирования (корпус запросов из AC-5) до фазы 3 — рекомендуется да.
