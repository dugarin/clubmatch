# ADR-002: Интеграция Telegram (аутентификация Mini App, бот-уведомления)

Статус: accepted (2026-10-30, опросник 07: Q-2.1…Q-2.4)
Дата: 2026-10-30
Контекст: roadmap 2.3. Требования:
- Аутентификация — только через Telegram: валидация `initData` Mini App (NFR-7); бот не является каналом аутентификации и подачи заявки.
- Уведомления через бота ≤ 1 мин после события: матч, одобрение/отклонение заявки, отзыв тега у автора, потеря анкетой последнего навыка (NFR-12, FR-4, FR-8); при недоставке — повтор при первой возможности. Уведомления о решении по заявке — только при наличии связки кандидата с ботом (NFR-12, редакция spec 1.1, решение владельца 2026-10-30).
- При недоставке уведомления контакт остаётся доступным в Mini App (FR-8, UC-4 E2).
- Масштаб: ≤ 50 одновременных сессий (NFR-4) → объём уведомлений мал.

Ограничение платформы: Bot API не позволяет отправить сообщение пользователю, не начавшему диалог с ботом (`chat_id` появляется только после `/start` или взаимодействия) → шаг «запустить бота» должен быть частью онбординга `[умозаключение]`, иначе NFR-12 недостижим для новых участников.

## Альтернативы

### А. Приём событий бота

| Вариант | Плюсы | Минусы | Стоимость выхода |
|---|---|---|---|
| Webhook на существующий API backend | Нет отдельного компонента; HTTPS-ендпоинт уже есть для Mini App; мгновенная доставка `/start` | Нужен публичный URL с валидным TLS (он и так нужен Mini App) | Низкая: смена метода — одна команда setWebhook/deleteWebhook |
| Long polling worker | Работает без публичного URL; проще локальная разработка | Отдельный долгоживущий процесс; задержка до интервала опроса | Низкая |

### Б. Очередь и повторы уведомлений

| Вариант | Плюсы | Минусы | Стоимость выхода |
|---|---|---|---|
| Outbox-таблица в Postgres + worker (ретраи с backoff) | Ноль новых компонентов (ADR-001: один stateful); транзакционная запись события вместе с бизнес-операцией (матч/решение модератора); повтор «при первой возможности» — естественный select по `next_attempt_at` | Свой код ретраев; worker — ещё один процесс | Низкая: таблица и worker — внутренние детали |
| Redis + очередь (Dramatiq/Celery, BullMQ) | Готовые ретраи, дашборды | Второй stateful-компонент против решения ADR-001; избыточно для NFR-4 | Средняя: смена брокера и клиентского кода |
| Синхронная отправка в транзакции запроса | Проще всего | Падение Bot API ломает бизнес-операцию; нарушает «≤1 мин» при деградации API; нет повторов | Низкая, но отвергнуто по NFR-12 |

### В. Валидация initData

Вариант один по протоколу Telegram: HMAC-SHA256(`secret_key` = SHA256(bot_token)), проверка подписи полей `initData` + свежесть `auth_date`. Альтернативы нет — механизм задан платформой; выбор только библиотеки под принятый стек (Go, ADR-001) — фиксируется на фазе 3, на архитектуру не влияет.

## Критерии

- Не добавлять stateful-компоненты сверх ADR-001.
- NFR-12: ≤ 1 мин до первой попытки; повторы до успеха или до недоступности канала.
- Бот — только уведомления и `/start`-связка; никакой бизнес-логики через бота (NFR-7).
- Недоставка не блокирует функции Mini App (FR-8).

## Решение-кандидат

1. **Аутентификация**: backend валидирует `initData` каждого запроса Mini App (подпись + TTL `auth_date` 24 ч — утверждено владельцем 2026-10-30); сессий/паролей нет; идентичность — `telegram_user_id` из валидированного initData.
2. **Связка бота**: шаг онбординга — deep-link `t.me/<bot>?start=<nonce>` из Mini App (утверждено владельцем 2026-10-30, внесено в UC-1 шаг 5); по `/start` backend связывает `chat_id` с User; без связки уведомления недоступны, контакт — только в Mini App (не блокер онбординга). Кандидат до онбординга связки не имеет → уведомления о решении по заявке ему не доставляются (NFR-12 spec 1.1; экран заявки в Mini App показывает статус при повторном входе — основной канал для кандидата) `[предположение: статус заявки виден в Mini App]`.
2a. **Ссылки-приглашения**: формат `https://t.me/<bot>/<miniapp>?startapp=<invite_token>` — токен приходит в Mini App в start-параметре и передаётся в `POST /profiles` при онбординге; одноразовость проверяется на backend (FR-13, ревью F2).
3. **Уведомления**: outbox-таблица `notification` (`type`, `user_id`, `payload`, `state`, `attempts`, `next_attempt_at`) в той же транзакции, что и событие (матч, решение по заявке, отзыв тега). Worker раз в ≤30 c `[предположение]` выбирает due-записи и отправляет через Bot API; backoff экспоненциальный, параметры — конфигурация (дефолты: 1 мин → 5 → 15 → 60, далее раз в час; утверждено владельцем 2026-10-30).
4. **Недоставка**: ошибки 403 (бот заблокирован) → `state=blocked`, повторная попытка при следующем `/start` или смене состояния бота; матч и контакт в Mini App не затрагиваются (FR-8).
5. **Приём событий**: webhook на том же API backend (только `/start` и минимум команд); polling — fallback для dev-окружения. Webhook защищается `secret_token` (заголовок `X-Telegram-Bot-Api-Secret-Token`, задаётся при `setWebhook`) — без валидного секрета запрос отклоняется 401 (ревью F12).

## Принятые компромиссы (trade-offs)

- Свой worker ретраев вместо готового брокера — код, который нужно тестировать (порядка 100 строк `[умозаключение]`).
- Webhook требует публичного TLS-ендпоинта — он и так обязателен для Mini App, дополнительной поверхности не даёт.
- Кандидаты без связки с ботом не получают уведомления о решении по заявке — принято владельцем как ограничение NFR-12 (spec 1.1, 2026-10-30); компенсация — статус заявки в Mini App.

## Риски

| Риск | Severity | Митигация |
|---|---|---|
| Участник не запускает бота → уведомления недоставлены | medium | Шаг онбординга с deep-link; периодический баннер в Mini App (поле `bot_linked` в API, ревью F11); контакты доступны без бота (FR-8) |
| Кандидат без связки не узнает о решении по заявке | low | Принятое ограничение (NFR-12 spec 1.1); статус заявки в Mini App |
| Блокировка бота пользователем → 403 навсегда | low | `state=blocked` + повтор при возобновлении диалога; журнал попыток |
| Подделка initData при ошибке валидации | high | Единая проверенная реализация проверки подписи; тест на tampered-подпись; TTL auth_date |
| Лимиты Bot API (30 msg/s) | low | Недостижимы при NFR-4 (1k участников); worker шлёт последовательно |

## Условия пересмотра (reopen conditions)

- Появление второго stateful-компонента по другим причинам (кэш/сессии) → пересмотр outbox в пользу брокера.
- Требование интерактивных сценариев в боте (кнопки, заявки через бота) → отдельный ADR, противоречит текущему NFR-7.
- Требование доставлять уведомления о заявках всем кандидатам → пересмотр: deep-link при подаче заявки (альтернатива F1, отклонённая владельцем 2026-10-30).
