# ADR-003: Поиск и ранжирование

Статус: accepted (2026-10-30, опросник 07: Q-3.1…Q-3.3); изменено 2026-10-31 — решение владельца: MVP-поиск только по тегам (уровень 1), полнотекст (уровень 2) — post-MVP (FR-10 spec 1.2)
Дата: 2026-10-30
Контекст: roadmap 2.4, зависит от ADR-001 (PostgreSQL). Требования FR-10/FR-11 (Р2):
- Свободный запрос 1–256 символов, нормализация (нижний регистр, `ё`→`е`, пробелы), морфология рус.+англ.
- Синонимы — через справочник тегов (canonical + алиасы).
- Ранжирование: точное совпадение тега > совпадение свободного текста; приоритет полей навыки > проекты > проф. интересы > личные интересы; внутри группы — ранг FTS.
- Пагинация по 10; фильтры: локация (точное совпадение нормализованной строки), формат встречи (`any` удовлетворяет любому фильтру).
- Своя анкета исключена; оценённые карточки — с меткой оценки; анкеты без навыков (`is_searchable=false`) исключены (FR-4).
- NFR-2: ≤ 5 с p95 при ≤ 1 000 участников — с огромным запасом `[умозаключение]`.

## Альтернативы

| Вариант | Плюсы | Минусы | Стоимость выхода |
|---|---|---|---|
| A. PostgreSQL FTS (tsvector с весами + справочник тегов) | Один запрос SQL; веса полей нативны (A/B/C/D); нет новых компонентов | Формула ранжирования — ручной SQL; двуязычная морфология требует спайка | Низкая (внутри ADR-001) |
| B. Ранжирование в приложении (выборка кандидатов SQL, скоринг в коде) | Гибкая формула, легко тестировать | Тащим кандидатов в память; пагинация усложняется; при росте — проблема | Средняя |
| C. pg_trgm similarity | Нечёткость (опечатки) | Не даёт морфологии и весов полей как tsvector; другое ранжирование | Низкая |

## Критерии

- Воспроизводимая, тестируемая формула ранжирования (AC-5).
- Пагинация стабильна между страницами.
- Соответствие ADR-001 (без новых компонентов).

## Решение-кандидат

**Вариант A** — один параметризованный SQL-запрос:

1. **Индекс анкеты** (материализуемый в колонках, обновление триггером или при записи; изменения ≤ 1 мин по FR-3):
   - `tag_doc`: точные нормализованные значения тегов через справочник (canonical ∪ алиасы), раздельно по kind.
   - `fts_doc`: tsvector с весами — навыки=A, проекты=B, проф. интересы=C, личные интересы=D.
   - Двуязычие (уточнено спайком T-2, 2026-10-30, [fts-bilingual](../spikes/fts-bilingual.md)): **один вектор одной конфигурации** — `to_tsvector('russian', t)`; штатный маппинг токенов `russian` сам направляет латиницу в `english_stem` (проверено: 0 расхождений в совпадениях против конкатенации ru||en на корпусе спайка). Конкатенация конфигураций и отдельные колонки `fts_ru`/`fts_en` не нужны — дублируют лексемы и искажают ранги.
2. **Обработка запроса**: нормализация → разбор на термы → **стемминг термов** той же конфигурацией `russian` (уточнено спайком T-2, 2026-10-30): механизм — Snowball-стемминг, не лемматизация ('кафкой' → 'кафк', а не 'кафка'; 'deployments' → 'deploy'); для сопоставления достаточно, т.к. обе стороны стеммятся одинаково. Терм стеммится вызовом `to_tsvector('russian', term)` — конфигурация сама выбирает словарь по алфавиту; стоп-слова дают пустой вектор (фильтруются) — иначе «кафкой» не совпадёт с алиасом «кафка» и флагманский AC-5 не пройдёт (ревью F3; кейс «кафкой» обязателен в спайке T-3) →
   - *Уровень 1 (точный тег)*: стеммированные термы, совпадающие со стеммированным алиасом тега — алиасы хранятся нормализованными + стеммированными: колонка `lexemes text[] = tsvector_to_array(to_tsvector('russian', normalized))` (подтверждено спайком T-2, 2026-10-30); совпадение: равенство лексем для однословного алиаса, `lexemes <@ lexemes(запроса)` для мультисловного → анкеты с этим тегом, буст выше любого FTS-ранга; внутри — приоритет kind (skill > prof > personal). Ограничение: кириллица запроса не матчит латинское написание в свободном тексте ('кафкой' не находит 'kafka' в проектах) — связывание только через алиасы уровня 1 (подтверждено спайком T-2).
   - *Уровень 2 (FTS)*: `websearch_to_tsquery('russian', ...)` (один запрос, конфигурация двуязычна — спайк T-2), ранг `ts_rank_cd` с массивом весов `{D, C, B, A}` по схеме приоритетов. Спайк T-2 показал: сырой `rank` не гарантирует приоритет полей (ничья B=0.4 и C=0.4 при суммировании совпадений) → `field_group` (максимальный вес совпавшего поля) вычисляется явно, напр. серией `ts_rank_cd('{0,0,0,1}', v, q) > 0` → A, иначе `'{0,0,1,0}'` → B и т.д. Также: AND-семантика `websearch_to_tsquery` («разобраться с кафкой» → `'разобра' & 'кафк'`) требует всех стемов — поведение при пустом AND-результате (OR-фолбэк?) решается на корпусе T-3.
   - Предикаты выборки (явно, ревью F16): `profile.user_id != viewer_id` (своя анкета исключена, FR-10) и `is_searchable = true` (FR-4).
   - Итоговый ключ сортировки: `(tag_boost DESC, field_group, rank DESC, profile_id)` — детерминированный; пагинация **offset** (утверждено владельцем 2026-10-30; при 1k анкет «прыжки» карточек между страницами приемлемы).
3. **Фильтры**: `location_norm = $n` (точное), `meeting_format = $f OR meeting_format = 'any'` (FR-11).
4. **Обогащение выдачи**: метка текущей оценки — join с Evaluation по (viewer, target); входящие «интересно» не отдаются (FR-7).
5. **Пустой результат**: 200 + `[]` + флаг `filters_applied` для подсказки «смягчить фильтры» (FR-10).

Колода (FR-5) — тот же механизм совпадения тегов: группа 1 — карточки с совпадением (skill/prof > personal), группа 2 — остальные, внутри группы `random()`; исключены: своя анкета, оценённые за 30 дней (FR-9), не-searchable (FR-4).

Решение принято владельцем 2026-10-30 (опросник 07). Уточнено спайком T-2, 2026-10-30 ([fts-bilingual](../spikes/fts-bilingual.md)): схема двуязычия упрощена до одной конфигурации `russian` (вместо конкатенации ru||en); деталь стемминга уровня 1 (стемы Snowball, хранение `lexemes` в tag_alias) подтверждена; добавлены требования к вычислению `field_group` и фиксация AND-семантики запроса. Статус ADR не меняется (accepted).

## Принятые компромиссы (trade-offs)

- Формула в SQL — читаемость ниже, чем код приложения; компенсируется тестовым корпусом AC-5.
- Триггерное обновление `fts_doc` усложняет запись анкеты; альтернатива — пересчёт в приложении при сохранении (FR-3 ≤ 1 мин легко выполняется).
- Опечатки/нечёткость не поддержаны (только морфология и алиасы) — осознанный non-goal MVP (утверждено владельцем 2026-10-30).
