# ADR-004: Видимость полей и приватность

Статус: accepted (2026-10-30, опросник 07: Q-4.1, Q-4.2)
Дата: 2026-10-30
Контекст: roadmap 2.5. Требования:
- FR-14: состав карточки до/после матча по таблице видимости; скрытые поля **не передаются клиенту** (NFR-8, AC-7).
- FR-7: входящее «интересно» не раскрывается до взаимности — ни в UI, ни в API (Q19).
- FR-17: удаление анкеты → удаление анкеты/оценок/матчей; контакт у второй стороны — «недоступен».
- Р8/NFR-10: журнал раскрытия контактов, хранение 1 год независимо от удаления анкеты.

## Альтернативы

| Вариант | Плюсы | Минусы | Стоимость выхода |
|---|---|---|---|
| A. Server-side DTO-политика (сборка ответа по матрице видимости в сервисном слое) | Один источник правды — матрица FR-14 в коде; простые тесты AC-7 (контрактные); не зависит от СУБД | Дисциплина: любой новый эндпоинт обязан проходить через политику | Низкая |
| B. Представления БД (views до/после матча) | Фильтрация на уровне данных; нельзя «забыть» поле в SQL | Логика видимости размазана SQL↔код; сложно версионировать; отладка хуже | Средняя |
| C. Клиентская фильтрация | Нет | Прямое нарушение NFR-8/AC-7 | — (отвергнуто) |

## Критерии

- Скрытое поле физически отсутствует в ответе (не `null`, а отсутствует) — проверяемо контрактным тестом.
- Единая точка применения правил видимости.
- Удаление анкеты и журнал — транзакционно согласованы.

## Решение-кандидат

**Вариант A**:

1. **Матрица видимости** — кодовая константа, 1:1 таблица FR-14 (ключ: поле × состояние отношения viewer↔owner: `self | pre_match | matched | moderator`). Модератор видит состав `pre_match` + служебные поля заявки; контакта до матча нет ни у кого, включая модератора (FR-15).
2. **Точка применения**: все ответы с данными анкеты (колода, поиск, матчи, карточка) строятся сериализатором, принимающим (viewer, owner, match_state) и включающим только разрешённые поля; SQL дополнительно не выбирает `telegram_username`/`telegram_user_id` для pre_match-выдачи (двойной контур).
3. **Оценки**: API никогда не отдаёт входящие оценки; в ответах — только собственная оценка viewer'а (метка в поиске, FR-9/FR-12).
4. **Раскрытие контакта**: запись в ContactDisclosureJournal создаётся в транзакции создания матча (обе стороны) и при каждой фактической выдаче контакта в разделе «Матчи» (утверждено владельцем 2026-10-30: журналируется каждая выдача).
5. **Удаление анкеты (FR-17)**: в одной транзакции — удаление Profile, ProfileTag, Project, Evaluation (обе стороны), перевод Match в `contact_unavailable`, `deleted_at` у User; журналы (раскрытие, модерация) не трогаем (NFR-10), в них — денормализованный снапшот `telegram_user_id`.
6. **Согласие (FR-16)**: Consent-запись — обязательное условие завершения онбординга (CHECK в сервисном слое; транзакция создания анкеты).

Решение — кандидат до принятия владельцем.

## Принятые компромиссы (trade-offs)

- Политика в коде, а не в БД → обязательные контрактные тесты на каждый эндпоинт с данными анкеты (включены в план тестирования фазы 3).
- Журнал выдачи контакта растёт при каждом открытии «Матчей» — при 1k участников несущественно `[умозаключение]`; можно журналировать только первую выдачу (вопрос владельцу).

## Риски

| Риск | Severity | Митигация |
|---|---|---|
| Новый эндпоинт обходит политику и утекает скрытое поле | high | Единый сериализатор анкеты; линтер/правило ревью «нет прямых ответов из ORM»; контрактные тесты AC-7 обязательны для каждого такого эндпоинта |
| Гонка «матч ↔ удаление анкеты» | medium | Обе операции транзакционны; проверка состояния матча при выдаче контакта |
| Снапшот в журнале устаревает | low | Журнал — факт прошлого раскрытия, актуальность не требуется |
