# Спайк T-2: двуязычный полнотекстовый поиск PostgreSQL 16

Задача 3.1.1 ([phase-3-plan](../phase-3-plan.md)). Контекст: [ADR-003](../architecture/adr-003-search-ranking.md)
(уровни 1/2, ревью F3), [ADR-001](../architecture/adr-001-storage-stack.md) (вопрос 3),
FR-10/FR-11, AC-5. Дата выполнения: 2026-10-30. Статус: **выполнен**.

## Среда

- `docker compose up -d db` → `postgres:16-alpine`, фактически PostgreSQL 16.15
  (x86_64-pc-linux-musl); БД/юзер `clubmatch`. После спайка стек остановлен (`docker compose down`).
- Запросы выполнялись через `docker compose exec -T db psql -U clubmatch -d clubmatch -v ON_ERROR_STOP=1`.

## Постановка (что проверялось)

1. Один tsvector `to_tsvector('russian', t) || to_tsvector('english', t)` + `websearch_to_tsquery`
   по обоим словарям: совпадения рус./англ. термов, аномалии позиций/весов (`ts_rank_cd`, веса {D,C,B,A}).
2. Лемматизация термов запроса для уровня 1 (точный тег): `ts_lexize('russian', 'кафкой')` → 'кафка'?,
   `ts_lexize('english', 'deployments')` → 'deploy'? Пригодность для сопоставления с алиасами тегов.
3. Смешанный запрос «разобраться с кафкой»: анкета с тегом Kafka/Кафка выше анкеты
   с «кафкой» только в проектах; веса навыки A > проекты B > проф. интересы C > личные D.
4. Кириллица в английском словаре и наоборот ('sdd', 'kafka' в русском тексте).

## Фактические результаты

### 1. Комбинированный вектор ru||en — работает, но избыточен

```sql
select to_tsvector('russian', 'разобраться с кафкой и Kafka deployments')
    || to_tsvector('english', 'разобраться с кафкой и Kafka deployments');
-- 'deploy':6,12 'kafka':5,11 'и':10 'кафк':3 'кафкой':9 'разобра':1 'разобраться':7 'с':8
```

- Позиции **не пересекаются**: оператор `||` сдвигает позиции второй части (ru заняла 1..6,
  en — 7..12). Аномалий позиций нет; фразовый запрос `phraseto_tsquery('english','data engineer')`
  по комбинированному вектору матчится корректно.
- Веса (`setweight(..., 'A')` …) сохраняются при конкатенации.
- Лексемы дублируются: 'kafka':5,11 — en-часть хранит кириллицу нестеммированной ('кафкой':9),
  что даёт лишние совпадения по «сырой» форме, но не добавляет стемминг-совпадений.

**Ключевой факт (маппинг токенов конфигурации `russian`):**

```sql
select tt.alias, d.dictname from pg_ts_config_map m
  join ts_token_type('default') tt on tt.tokid = m.maptokentype
  join pg_ts_dict d on d.oid = m.mapdict
 where m.mapcfg = 'russian'::regconfig order by 1;
-- asciiword | english_stem   <- латиница стеммится АНГЛИЙСКИМ словарём
-- word      | russian_stem   <- кириллица — русским
-- hword_part| russian_stem; hword_asciipart | english_stem; остальное — simple
```

Штатная конфигурация `russian` уже двуязычна. Проверка эквивалентности на корпусе
(5 текстов × 10 запросов: 'кафкой','кафка','kafka','deployments','deployment','sdd',
'миграции','разобраться','databases','automation'):

```sql
-- расхождений в @@ между to_tsvector('russian',t) и ru||en при запросе websearch_to_tsquery('russian',q):
-- 0 строк
select to_tsvector('russian','разобраться с кафкой и Kafka deployments')
       @@ websearch_to_tsquery('russian','kafka');       -- t
-- то же для 'deployment' и 'кафкой'                     -- t, t
```

Вывод по п.1: комбинированный вектор ru||en и второй запрос не нужны — достаточно
одного вектора `to_tsvector('russian', ...)` и одного запроса `websearch_to_tsquery('russian', ...)`.
Комбинированный вектор лишь удваивает размер и искажает ранги дубликатами лексем.

### 2. «Лемматизация» уровня 1 — это стемминг Snowball, и его достаточно

`ts_lexize` принимает имя **словаря** (`russian_stem`/`english_stem`), не конфигурации
(`ts_lexize('russian', ...)` → ERROR: text search dictionary "russian" does not exist).

```sql
select ts_lexize('russian_stem', 'кафкой');      -- {кафк}   (не 'кафка'! стем, не лемма)
select ts_lexize('russian_stem', 'кафка');       -- {кафк}   -> совпадает с формой 'кафкой'
select ts_lexize('russian_stem', 'разобраться'); -- {разобра}
select ts_lexize('russian_stem', 'миграции');    -- {миграц}
select ts_lexize('english_stem', 'deployments'); -- {deploy}
select ts_lexize('english_stem', 'databases');   -- {databas}
select ts_lexize('english_stem', 'running');     -- {run}
```

- Ожидание «'кафкой' → 'кафка'» из постановки **не подтвердилось дословно**: результат — стем
  'кафк'. Для сопоставления это не важно: обе стороны (алиас и терм запроса) стеммятся
  одинаково, сравнение идёт по стемам.
- Неизвестное слово возвращается **неизменённым, не NULL**:
  `ts_lexize('russian_stem','kafka')` → `{kafka}`, `ts_lexize('english_stem','кафка')` → `{кафка}`.
- Стоп-слова дают пустой массив: `ts_lexize('russian_stem','с')` → `{}` (надо фильтровать).

**Рекомендуемая механика уровня 1** — не `ts_lexize` по словарям вручную, а та же
конфигурация, что и для FTS (сама выбирает словарь по алфавиту токена):

```sql
select to_tsvector('russian','кафкой') = to_tsvector('russian','Кафка');   -- t  (алиас матчится)
select to_tsvector('russian','deployments') = to_tsvector('russian','deploy'); -- t
select to_tsvector('russian','кафкой') = to_tsvector('russian','Kafka');   -- f  (кириллица ≠ латиница,
                                                                             --  связывается списком алиасов)
-- мультисловный алиас ('data engineer'): все лексемы алиаса ⊆ лексем запроса:
select tsvector_to_array(to_tsvector('russian','data engineer'))
       <@ tsvector_to_array(to_tsvector('russian','ищу data engineer для проекта')); -- t
```

Итог по п.2: подходит. Алиасы хранить нормализованными + стеммированными
(`to_tsvector('russian', normalized)`), термы запроса стеммить тем же вызовом,
совпадение = равенство лексем (однословный алиас) или `<@` по массивам лексем (мультисловный).

### 3. Смешанный запрос «разобраться с кафкой» — уровень 1 решает, ранг требует field_group

Стенд (temp-таблицы): тег Kafka с алиасами Kafka/kafka/Кафка/Кафкой (стемы — как в п.2),
5 анкет: (1) навык-тег Kafka, (2) «кафку» только в проектах, (3) «Кафка» в проф. интересах,
(4) «Кафка» в личных интересах, (5) нерелевантная.

```sql
select websearch_to_tsquery('russian','разобраться с кафкой'); -- 'разобра' & 'кафк'  (AND!)
-- уровень 1: терм 'кафкой' -> to_tsvector -> {'кафк'} = стем алиаса 'Кафка' -> тег Kafka
-- уровень 2: веса {D,C,B,A} = {0.1,0.2,0.4,1.0}, ts_rank_cd
```

Результат конвейера (tag_boost DESC, fts_rank DESC):

| id | анкета | tag_boost | fts_rank | fts_match |
|----|--------|-----------|----------|-----------|
| 1  | tag_kafka_skill | 1 | 0.0000 | f |

Отдельно по запросу «кафка» (уровень 2, приоритет полей):

| анкета | rank_ru | rank_en | rank_sum |
|--------|---------|---------|----------|
| kafka_only_in_project (B) | 0.4000 | 0.0000 | **0.4000** |
| kafka_in_prof (C)         | 0.2000 | 0.2000 | **0.4000** |
| kafka_in_personal (D)     | 0.1000 | 0.1000 | 0.2000 |

Выводы по п.3:

- Флагманский кейс AC-5 работает: анкета с тегом получает `tag_boost=1` и идёт выше любой
  FTS-анкеты, даже имея fts_rank=0 (связь 'кафкой'→тег Kafka даёт именно уровень 1;
  FTS 'кафкой' по латинскому 'Kafka' в навыке не матчится — см. п.4).
- **Сырой `rank_sum` НЕ гарантирует приоритет полей**: B (0.4) и C (0.4) дали ничью —
  ru+en части в C сложились до уровня B. Подтверждена необходимость ключа сортировки
  ADR-003 `(tag_boost DESC, field_group, rank DESC)`, где `field_group` — максимальный вес
  совпавшего поля (вычисляется отдельно, например `ts_rank_cd('{0,0,0,1}',v,q)>0` → A,
  иначе `'{0,0,1,0}'` → B и т.д.).
- **AND-семантика** `websearch_to_tsquery`: полный запрос требует ВСЕ стемы → анкета 2
  («кафку» в проектах, без «разобраться») полным запросом не матчится FTS вообще
  (из финальной выборки она выпала). Уровень 1 закрывает AC-5, но поведение «нет совпадений
  из-за глагола запроса» — вход для T-3 (корпус): кандидаты — OR-фолбэк при пустом
  AND-результате либо принятие как есть `[решение — в задаче 3.1.2]`.
  (Анкеты 3/4 в стенде не бустятся, т.к. mock хранил сырые значения вместо canonical tag_id —
  артефакт стенда; в реальной схеме profile_tag ссылается на canonical тег.)

### 4. Перекрёстные случаи

```sql
select to_tsvector('russian','sdd kafka deployments databases running');
-- 'databas':4 'deploy':3 'kafka':2 'run':5 'sdd':1   (латиница стеммится english_stem)
select to_tsvector('english','кафка кафкой разобраться миграции');
-- 'кафка':1 'кафкой':2 'миграции':4 'разобраться':3  (кириллица хранится СЫРОЙ — бесполезно)
```

- 'sdd'/'kafka' в русском тексте матчатся одиночной russian-конфигурацией с любой стороны — обработка не нужна.
- **Кириллический запрос не матчит латинское написание в тексте**:
  `vec('разобраться с kafka') @@ websearch_to_tsquery('russian','кафкой')` → **f**.
  Связывание 'кафка'↔'kafka' — только через алиасы тегов (уровень 1). В свободном тексте
  (проекты) 'kafka' по запросу 'кафкой' не найдётся — осознанное ограничение схемы.
- Регистр не проблема: 'Kafka' → 'kafka' конфигурацией. `ё`→`е`: 'вёрстка' и 'верстка'
  стеммятся одинаково ({верстк}) уже без нормализации, но нормализация на запись
  остаётся по FR-10 (единообразие с location и дедупликацией тегов).
- Смешанный скрипт в одном токене ('kafkа' с кириллической 'а') — один токен,
  не стеммится ни одним словарём ('kafkа':1,2); краевой случай, ловится только точным
  написанием. Митигация не требуется для MVP `[умозаключение]`.

## Вывод: вариант схемы

**Подтверждён вариант «один вектор» — но без конкатенации конфигураций:**
одна конфигурация `russian` (она сама направляет латиницу в `english_stem`),
один вектор на анкету с весами A/B/C/D, один запрос `websearch_to_tsquery('russian', ...)`.
Отдельные колонки `fts_ru`/`fts_en` и сумма рангов **не нужны** (расхождений в совпадениях
нет, а ранги комбинированный вектор искажает дубликатами).

### Рекомендуемые колонки для миграции 3.2.1

```sql
-- profile: материализуемый FTS-документ (обновление при записи анкеты/тегов)
fts_doc tsvector NOT NULL DEFAULT ''::tsvector
-- наполнение: setweight(to_tsvector('russian', skills_text),   'A') ||
--             setweight(to_tsvector('russian', projects_text), 'B') ||
--             setweight(to_tsvector('russian', prof_text),     'C') ||
--             setweight(to_tsvector('russian', personal_text), 'D')
-- индекс: CREATE INDEX ... USING gin (fts_doc);

-- tag_alias: нормализация + стемминг для уровня 1
normalized  text   NOT NULL,           -- нижний регистр, ё->е, сжатые пробелы (unique)
lexemes     text[] NOT NULL            -- tsvector_to_array(to_tsvector('russian', normalized))
-- однословный алиас: совпадение = lexemes = lexemes(терм запроса)
-- мультисловный алиас: lexemes <@ lexemes(весь запрос)
```

Детали для 3.4.4: ключ сортировки `(tag_boost DESC, field_group, rank DESC, profile_id)` —
`field_group` вычислять явно (см. п.3), `rank` = `ts_rank_cd('{0.1,0.2,0.4,1.0}', fts_doc, query)`.
Стоп-слова запроса дают пустые лексемы — фильтровать до сопоставления с алиасами.
